2. The reconcile finding (real)

The narrative assurance passport (lib/content/productNarratives.ts) summarises five domains. Traced against the granular record in content/apps/luscii.json, four line up. One overstates.

Assurance domain (summary)Status nowGranular JSON backingReconciled?

The conflict. The passport marks Data protection and IG as “Verified — current” on the strength of DTAC + DSP Toolkit, but the granular record has ISO 27001 and Cyber Essentials “not confirmed in reviewed sources” and a DPIA still required (AWS Germany hosting). A commissioner opening the Safety & governance tab would see a weaker picture than the green summary chip implies. R3-3 decides how to close this.

R3-1 — Assurance passport placement

Where does the “national assurance, reuse the passport” summary live, relative to the existing granular Safety & governance tab?

Option A — new section in the spine rec Chosen

An “Assurance” PdpSection after How-to-buy, before the tabs. Matches the R1/R2 spine pattern; deep detail stays in the Safety & governance tab.

Option B — top of the Safety tab

Passport sits above the granular rows inside the existing tab. Keeps all governance in one place; loses the spine narrative beat.

Option C — snapshot chip strip

A compact row of domain status chips near the commissioning snapshot; full passport in the tab. Very scannable; least room for the “reuse” message.

Option D — both spine + tab

Summary in the spine and reframed detail at the top of the tab. Most complete; some duplication to keep in sync.

R3-2 — Assurance passport styling

The existing AssurancePassport.tsx is built with NHS.UK frontend classes (nhsuk-table, nhsuk-tag, nhsuk-warning-callout). The spine everywhere else uses the PDP design tokens (PdpSection, hs-*, var(--nhs-blue)). Which look wins?

Option A — restyle to PDP tokens

Rebuild the passport with hs-* cards. Fully consistent with the spine; drops the nhsuk table.

Option B — mount nhsuk as-is

Use the component unchanged. Zero rebuild; visually foreign inside the spine.

Option C — PDP cards + material-gap callout rec

PDP-styled domain cards for the summary, but keep the explicit “material assurance gaps” callout behaviour. Consistent and keeps the safety-first surfacing.

Option D — status chips, table expandable Chosen

One row of domain chips; full table behind a “show detail” expander. Most compact. Chosen build — the material-gap callout is kept above the toggle so safety issues stay visible.

R3-3 — Reconcile: summary vs granular record

Given the IG conflict in section 2, how do we keep the summary and the detail honest and in step?

Option A — summary is source of truth

Narrative domains lead; JSON is just detail. Simple, but lets the summary overstate (the current bug).

Option B — leave both independent

Author maintains each by hand. No new work now; the drift stays.

Option C — auto-derive from JSON Chosen

Compute domain statuses from the granular fields. Always in step; loses the curated summary voice. Chosen over rec D — structurally prevents drift and needs no per-product authoring, which suits R3-4 D.

Option D — reconcile now + mapping rec

Keep the hand-authored summary but fix it now: downgrade IG to review due with a residual action, and publish the domain→JSON mapping (section 2) as the check.

R3-4 — Templatise: which products light up

The spine is gated by slug === 'luscii'. Curated narratives already exist for luscii, mycopd, myheart and joint-academy. Local reference/ROI data exists only for COPD. How far do we open it?

Option A — Luscii only (code refactor)

Generalise the structure but keep the gate on Luscii. Safest; no new products go commissioner-facing.

Option B — all four curated

Turn on luscii, mycopd, myheart, joint-academy. Biggest payoff; each needs a reconcile pass first.

Option C — COPD only

luscii + mycopd, where the local value block has real data. Coherent set; leaves myheart/joint-academy for later.

Option D — data-driven gating rec Chosen

Spine + assurance show for any product with a curated narrative; the local-value block self-gates to COPD (already does via isCopd). One rule, no per-slug list.

R3-6 — Evidence schema normalise (roadmap item)

The Round 1 roadmap listed “normalise evidence schema” (n→sample_size, key_results→outcome, url_full_text→url). That assumed the matt_demo field names. On this branch it’s already consistent.

Verified. EvidenceCard in app/apps/[slug]/pdpBlocks.tsx reads study.n, study.key_results and study.url_full_text, and luscii.json → clinical_evidence_detailed uses exactly those keys. The full evidence record renders today. No rename needed.

Option A — verify & close as no-op rec Chosen

Done above — nothing to change on this branch.

Option B — rename to newer keys

Rename fields across JSON + card for a “cleaner” schema. Churn with no user-facing gain.

Option C — add a normaliser layer

Map both schemas at read time. Only worth it if we later import matt_demo-shaped JSON.
