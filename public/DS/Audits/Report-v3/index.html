3. SurfaceCard + Widget shell Shipped

The product has good surface classes (.hs-surface-card, .app-card) but they are shadow-only — every consumer still hand-rolls rounded-xl border bg-white p-5 alongside them. Worse, the dashboard widgets repeat an identical header + body + footer-link shell.

3.1 Current duplication

hand-rolled rounded-xl border bg-white shadow-*
duplicated widget shells (Saved, EOI, Commissioned, QuickLinks, NewsList)
editorial / marketing cards (case-study, concept steps, funding)
.glass-card/.glass-panel — defined, never imported

3.2 Choice CARD-1 — how SurfaceCard is delivered

Option A — extend the CSS class (recommended)

Make .hs-surface-card own border + radius + padding (with --sm elevation + a padding modifier). Existing markup like <div class="hs-surface-card rounded-xl border p-5"> just drops the redundant utilities. Works in server components, smallest churn.

.hs-surface-card { border:1px solid var(--border);
  border-radius: var(--radius-lg); padding: 20px;
  box-shadow: var(--shadow-md); background: var(--card); }

Option B — React <SurfaceCard>

A component with elevation / padding / interactive props. More explicit and type-safe, but must be a client/island import at each site and is a bigger diff.

3.3 Choice CARD-2 — canonical card radius

Round 2 remapped Tailwind’s named radii, so today’s card rounded-xl now renders at 16px. The DS card role is 12px (lg).

A — lg 12px (recommended)
B — xl 16px (keep current)

Option A restores the pre-Round-2 card look and matches the radius doc; Option B keeps the rounder post-remap surfaces and updates the mapping to suit.

3.4 Choice CARD-3 — dashboard Widget shell

Option A — <WidgetShell> (recommended)

One component for the icon + title + count, body, footer link chrome shared by Saved / EOI / Commissioned / QuickLinks / NewsList. Removes ~5 copies.

Option B — SurfaceCard only

Promote the surface class but leave each widget to compose its own header/footer. Less abstraction, keeps the duplication.

4.2 Choice FORM-1 — how FormField is delivered

Option A — React <FormField> + inputs (recommended)

FormField owns label / hint / error wiring (auto id + aria-describedby + aria-invalid); TextInput/Select/Textarea share one styled base. Best for a11y correctness; org-settings already works this way.

Option B — CSS classes only

Ship .ds-field/.ds-input/.ds-select/.ds-textarea (already prototyped in the DS) into globals.css and apply by hand. Lower churn, but label/error/aria wiring stays manual at each site.

4.3 Choice FORM-2 — input focus treatment

Option A standardises the org-settings blue ring across all inputs; Option B leans on the existing global yellow :focus-visible outline and adds no per-input ring.

4.4 Choice FORM-3 — extract the AuthCard shell

Option A — <AuthCard> (recommended)

One shell (6px blue top bar + rounded-2xl + shadow-lg) shared by login & select-entity. Slot in logo, heading, form.

Option B — keep inline

Two screens only — leave the duplicated markup as is.

5.2 Choice BADGE-1 — how pill colours are delivered

Option A — tint modifier classes (recommended)

Add .badge-condition / .badge-topic (and reuse the existing palette) so ConditionTag, TopicPill and EditorialPills all render via classes — no inline colour.

Option B — centralised inline constants

Keep inline styles but move the colour objects into one shared module. Less CSS, but styling stays in JS and can’t be themed by token.

6. Unify Collapsible variants P3 Shipped

Three components solve the same show/hide problem with ~90% shared logic: CollapsibleSection (card + Show/Hide text), CollapsibleInline (top-border + Show/Hide), and ProductPageExpander (chevron header + hash deep-link + print hooks). The expander is currently orphaned — the PDP migrated to the flat PdpSection.

6.1 The three variants

Card variant

CollapsibleSection — Show/Hide text toggle

Card chrome with shadow + 12px radius.

Inline variant

CollapsibleInline — lighter, no card

Top-border separator, nests inside an existing card.

Full-width header button, elevation changes on open, deep-link + print registration.

6.2 Choice COLL-1 — how to unify

Option A — one <Collapsible variant> (recommended)

A single component with variant="card" | "inline" | "expander". Shared core: useId, open state, aria-expanded/aria-controls/hidden.

Option B — shared useCollapsible hook

Keep three components but extract the state + aria wiring into one hook. Less churn, but chrome stays duplicated.

6.3 Choice COLL-2 — ProductPageExpander (orphaned) fate

Option A — keep as expander variant (recommended)

Fold the chevron + hash deep-link + print registration into the unified component so the capability survives for future PDP detail.

Option B — delete it

It is unused at runtime — remove the dead code and keep only card + inline variants.

Default toggle affordance (COLL-3, proposed): Show/Hide text for card/inline, chevron header for expander.

Source: Collapsible sections; CollapsibleSection.tsx, CollapsibleInline.tsx, ProductPageExpander.tsx.
