Report · v3 (audit) · Round 8

Third UX audit

A fresh, full UX audit of the HealthStore product, taken with new eyes after Rounds 6–7 shipped the experience backlog from the v2 audit. Where v1 focused on component reuse and v2 on experience, this pass focuses on follow-through and coherence: whether the shipped patterns (toasts, error-vs-empty, the canonical primitives) have reached the destination pages and newer surfaces — the editorial home, the dual home / search, the AI advisor — or stopped at the first screen. Cookie consent is intentionally out of scope.

Naming. This is the third audit (hence “v3”), but the eighth report in the series. v1 and v5 are the audits; v2/v3/v4 and v6/v7 are the Round implementation records. This audit lives at /DS/Audits/Report-v8 under the Audits section.

1. Executive summary

The product is in genuinely good shape. The primitives from v1 are real and well-built, and the experience backlog from v2 has largely shipped: a top-centre toast / live-region service (components/ui/Toast.tsx) is wired into six providers, dashboard widgets tell errors apart from empty, the core forms run on FormField + Button, the PDP hero has a single primary action, the nav highlights correctly across the /apps branch, and destructive one-clicks are guarded. Those claims hold up against the code.

The problems have shifted again — from “experience” to follow-through and coherence. Good patterns shipped on the first screen but didn't propagate: the dashboard widgets distinguish error from empty, yet the full saved-apps and eoi-record pages they link to still render an empty state on a failed fetch. A second cluster is the newer surfaces added since v2 — the editorial public home, a signed-in hero search, the AI advisor — which roll their own buttons and inputs instead of the canonical primitives, and introduce a dual “home” with duplicated search. The remaining accessibility gaps are small but real (AI error role, a disabled-reason exposed only as a tooltip, heading-level skips on two main pages), and a password reveal that can't be reached by keyboard. As in v2, there is mild documentation drift: “standardised” and “shipped” claims are true for the surfaces they were applied to, but narrower than they sound.

2. What changed since the v2 audit

For full detail see the round records (R6, R7). Verified against the current code, the v2 backlog shipped as follows:

  • Shipped Toast / live-region service (top-centre, polite + assertive, optional Undo) wired into bookmarks, compare basket, share, and org-settings save (UX-01/02/06/08).
  • Shipped Error vs empty on dashboard widgets and stat tiles, with a tri-state status on the providers and a loading skeleton (UX-03/05).
  • Shipped Form migration: org-settings and select-entity onto FormField / Button / labelled role="radiogroup"; EOI contact fields editable when prefill is empty (FRM-01/02/03, A11Y-01/02/04).
  • Shipped PDP triage: one filled primary, demoted utility cluster, trimmed hero badges; snapshot strip wraps; compare grids scroll (RSP-01/02/03).
  • Shipped Nav & vocabulary: prefix active-state across /apps, org-settings breadcrumb, “DTx app” on PDP / compare / saved, Compare toggle “Add to compare” / “Added” (NAV-02/03, CNT-01/02).
  • Shipped Safe destructive actions: in-flight guards on saved-app remove and clear-data; compare “Clear all” with an Undo toast (UX-04/07/08).
  • Deferred Surfacing orphaned routes in nav (NAV-01) and removing the repeated PDP CTA (PDP-4) — both intentional decisions, still open.

This audit takes that as the baseline and looks for what's left, what didn't propagate, and what's newly visible on surfaces added since v2.

5. Accessibility findings

Strengths (carried forward / improved)

  • Skip link on every routed page (including login); global :focus-visible outline.
  • Modal centralises focus trap, scroll lock, escape and restore; the AI drawer, EOI, Clear-data and Share modals all use it.
  • Toast errors live in an assertive role="alert" region; success / info in a polite role="status" region.
  • Dashboard widget failures use role="alert" + retry; compare exposes a live count region and per-cell sr-only app names.
  • Button handles aria-busy, native disabled and an aria-disabled escape hatch; PdpTabs roving focus.

Residual gaps

IDIssueSev
A11Y-01The AI advisor error box is a plain <div> with no role="alert" / aria-live, so failures aren't announced. Open since v2 (A11Y-03).Medium
A11Y-02CompareToggleButton's disabled reason is exposed only via the title tooltip on the aria-disabled button — not reliably announced and invisible to sighted keyboard users. Add aria-describedby / visible helper text. (Confirms v2 A11Y-05.)Medium

6. Documentation vs code drift

The recurring meta-finding of this series: claims that are true but narrower than they read.

Claim (in DS / round records)Code reality
R6: “Error vs empty” shipped.True for the dashboard widgets & stat tiles; the destination saved-apps / eoi-record pages still render empty on a failed fetch (STA-01).
R7: Vocabulary “standardised on DTx app”.True for compare / saved / PDP body copy; the discovery surfaces (catalogue, apps hub, hero subhead) still say “apps” / “digital therapeutics” (CNT-01).
R3/R6: forms migrated to FormField.Core forms done; catalogue search + checkboxes and the AI input remain raw HTML (FRM-03/05).

Do

  • Scope completion claims to the surfaces actually touched (“dashboard widgets”, not “the app”).
  • Carry a shipped pattern through to the destination pages it implies.

Don't

  • Let “standardised” / “shipped” imply coverage the code doesn't have yet.
  • Ship new surfaces (home, AI, editorial) on bespoke buttons / inputs instead of the primitives.
