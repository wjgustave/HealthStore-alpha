Round 6 — experience & reliability

With the Round 2 primitives, Round 3 consolidation and Round 4 cleanup shipped, Round 6 turned to feedback and resilience: a shared toast / live-region service so actions say what happened, dashboard widgets that tell errors apart from genuinely empty, the last unmigrated forms moved onto FormField + Button with real programmatic labels, and an Expression-of-Interest form that lets people fill in missing contact details. This page started as a decision document (like v2, v3 and v4); the decision log now records the choices that were made and everything below has shipped. The only deviation from the recommended defaults was FB-2: toasts ship as a top-centre stack.

3. Toast / live-region feedback service P1 Shipped

Today every feature hand-rolls its own feedback. The audit found no centralised service: save/remove failures set BookmarkProvider.error but SaveToggleButton never shows it; the compare basket is silent on add/remove/blocked; only SharePagePanel announces copy success (via its own inline aria-live); org-settings and EOI success are visual-only with no assistive-tech announcement. This section designs one shared service and decides what to wire to it (UX-01, UX-02, UX-06).

3.1 Current feedback patterns (the fragmentation)

Save / remove (PDP, catalogue)Button label + aria-pressed onlyerror set but never surfaced; no success announcement

Copy link / address (Share)announce + role="status" (inline, modal-only)Bespoke; lost when modal closes; not reusable

3.2 Choice FB-1 — service shape & API

Option A — ToastProvider + useToast() hook (recommended)

A React context mounted in AppShell, exposing toast.success(), toast.error(), toast.info(). Idiomatic, testable, easy to call from any client component or provider. Renders toasts in a portal.

Option B — imperative singleton notify(msg, {type})

A module-level event emitter + one mounted <Toaster/>; callable without a hook. No provider wiring, but harder to test and less React-idiomatic; can fire before mount.

3.3 Choice FB-2 — placement & visual treatment

Both previews are live (static HTML mock-ups of the proposed NHS-styled toasts).

Option A — bottom-centre stack (recommended)

✓ Saved myCOPD to your saved apps.
! Couldn’t save — try again.

Thumb-reachable on mobile, away from the top nav; stacks upward, max ~3 visible.

Option B — top-right stack

i Link copied to clipboard.

Familiar desktop convention; can collide with the sticky nav / AI strip on small screens.

Shipped (FB-2): neither A nor B — toasts ship as a top-centre stack (same NHS-styled card + coloured left border), so they clear the sticky nav on desktop and stay centred and reachable on mobile.

3.4 Choice FB-3 — live-region semantics

Option A — dual regions: polite + assertive (recommended)

Success / info toasts live in a role="status" (polite) region; error toasts in a role="alert" (assertive) region so failures interrupt and are not missed. The visible toast is the live region.

Option B — single polite region

Everything announced politely from one region. Simpler, but errors may queue behind other speech and be missed.

3.6 Choice FB-5 — existing inline announcers

Option A — consolidate transient feedback, keep contextual regions (recommended)

Route one-off action feedback (copy, save) through the service and remove SharePagePanel’s bespoke announce. Keep the contextual sr-only count regions in CatalogueClient / CompareWorkspaceView (they describe ongoing list state, not events).

Option B — leave existing announcers in place

Only add toasts where there is nothing today; accept some duplication in Share.

4. Distinguish error from empty P1 Shipped

The live dashboard (DashboardV4) widgets fetch through BookmarkProvider / EoiProvider, which set an error value on failure but also reset to an empty array. The widgets ignore error, so a failed fetch looks identical to “you have nothing yet”. The stat tiles are worse: they show a misleading 0 during loading and on error (UX-03, UX-05).

4.2 Choice ERR-1 — provider state model

Option A — explicit status field (recommended)

Add status: 'loading' | 'error' | 'ready' to BookmarkProvider + EoiProvider alongside the existing error message. Widgets branch on status — unambiguous, and a later success clears it cleanly.

Option B — reuse isLoading + error

No new field; widgets treat error != null as the error branch. Smaller change, but a stale error after a later success can mislead unless carefully cleared.

4.4 Choice ERR-3 — where the state logic lives

Option A — teach WidgetShell the states (recommended)

Add optional loading / error / onRetry props (or a small WidgetState helper) so every widget renders loading / empty / error consistently without duplicating markup.

Option B — keep WidgetShell dumb

Each widget renders its own states inline. No API change, but the empty/error/retry markup is duplicated per widget.

4.6 Choice ERR-5 — expired session (401)

Both providers currently treat a 401 as “empty” (so logged-out browsing is calm, not alarming).

Option A — soft “session expired” on the dashboard (recommended)

Keep 401-as-empty for public browsing, but in the logged-in dashboard context treat a 401 as a soft notice (“Your session may have expired — refresh.”) rather than a blank widget.

Option B — keep 401-as-empty everywhere

No change; simplest, but an expired session on the dashboard still reads as “nothing saved”.

5. Migrate forms to FormField + Button P1 Shipped

OrgSettingsClient is the last big form still on bespoke parts: it has zero <label> elements (labels are <span> with no htmlFor), 8 raw <button>s, and a local Banner with no role/aria-live. Migrating it onto the Round 3 FormField and the canonical Button fixes the programmatic labels in one pass (FRM-01, A11Y-01). SelectEntityForm is already in better shape (fieldset/legend + wrapping labels + role="alert") and only needs light polish (FRM-03).

5.1 The label gap (live before / after)

Today — <span> label, not associated

Organisation name

Clicking the text does nothing; screen readers read an unlabelled edit field.

After — FormField with <label for>

Label is clickable and announced; aria-required / aria-invalid wired automatically.

5.2 Choice FRM-A — org-settings migration depth

Option A — full migration (recommended)

Replace the local Field/FieldLabel/TextInput/TextArea/NumberInput/Select with FormField + the shared controls (real <label for> on every input), and the 8 raw buttons with <Button>. Most consistent; deletes duplicate primitives.

Option B — a11y-only pass

Keep the local controls but add proper <label for> + ARIA and fix the Banner. Smaller diff, but leaves the duplicate form/button code in place.

5.3 Choice FRM-B — the org-settings Banner

Option A — toasts for save result + inline banner for persistent state (recommended)

Route save success / error through the §3 toast service; keep an inline role="status"/role="alert" banner only for persistent context (e.g. “Saving is unavailable — database not connected”).

Option B — just fix the Banner

Add role/aria-live to the existing Banner; don’t involve toasts. (Depends on §3 not shipping.)

5.4 Choice FRM-C — TagEditor & AddCondition inner controls

Option A — real labels via FormField (recommended)

Give each tag-add input and the “Add a condition” select a proper (visible or sr-only) label, and confirm every add/remove icon button has an aria-label.

Option B — aria-label only

Minimal: add aria-label to the inner input/select without restructuring into FormField.

5.5 Choice FRM-D — select-entity polish (FRM-03)

Option A — light polish, keep fieldset/legend (recommended)

Link the fieldset to its error via aria-describedby, add aria-required to the radios, and tidy the labels. Radios stay native — not a FormField use-case.

Option B — new radio-group FormField wrapper

Build a FormField-style fieldset/radio-group primitive and migrate select-entity onto it. More work + a new pattern, but consistent with text fields.

6. EOI contact fields editable when empty P1 Shipped

In ExpressInterestModal the four contact fields (name, role, organisation, email) are rendered readOnly and required, prefilled from the session. When the prefill is supplied this is fine — but if a value is empty, the field is locked: the user can’t type, yet required can block submit. There’s no recovery path (FRM-02). Note: the API currently re-reads contact identity from the session and ignores the form, so making fields editable also needs a submit/API decision.

6.1 The lock (live preview)

Prefilled — read-only (correct today)

Empty prefill — locked & required (the bug)

Read-only + required + empty → dead end.

Proposed — editable when empty

Editable because prefill was blank.

6.2 Choice EOI-1 — editability model

Option A — editable only when prefill is empty (recommended)

readOnly = Boolean(prefillValue). Verified session data stays locked; users only fill the gaps. Smallest behaviour change, fixes the dead end.

Option B — always editable

Drop readOnly entirely; prefill just seeds values the user can change. Most flexible, but lets people overwrite verified identity.

Option C — “Edit contact details” toggle

Fields stay read-only with an explicit unlock control that makes all four editable. More UI; clearer intent.

6.3 Choice EOI-2 — submit / API alignment

Option A — send contact fields, API prefers submitted values (recommended)

Include name/role/org/email in the POST body; the route uses submitted values when present, falling back to session prefill, and validates server-side. Edits actually persist.

Option B — keep API reading from session

Only non-identity fields (phone, etc.) stay editable; identity fields aren’t truly editable. Simpler, but largely negates FRM-02 for empty identity fields.

6.4 Choice EOI-3 — validation

Option A — required only when editable (recommended)

An editable+empty contact field shows a proper FormField error on submit; a read-only prefilled field never blocks. No more invisible validation dead ends.

Option B — relax required entirely

Drop required on contact fields; rely on server validation. Simplest client-side, weaker inline guidance.
