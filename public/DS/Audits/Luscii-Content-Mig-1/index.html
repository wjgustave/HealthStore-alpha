1. Executive summary

The two Luscii pages differ in architecture, not just copy. The matt_demo page is a curated commissioner narrative — a hand-written story object (LUSCII_NARRATIVE) rendered as one long scrolling argument: problem → how it helps → what it could mean locally → what it’s worth → assurance → how to deliver → proof → how to buy. It is personalised to the commissioner’s geography (projected impact and economics recompute against local population data) and includes an interactive COPD ROI scenario engine.

The nhs_ds page is a catalogue product detail page: a single, very rich luscii.json rendered into a hero, a commissioning snapshot strip, and six reference tabs (Overview, Evidence, Deployment, Safety & governance, Commercial, Technical). It is deeper on facts (granular IG/safety, integrations, pricing, onboarding, full evidence cards, deployment register, selective share/PDF, express-interest) but has no narrative spine, no localisation, and no economics modelling.

The headline finding: this is not a copy edit. Reaching the gold standard means adding a narrative layer and personalisation on top of nhs_ds’s catalogue data, while being deliberate about the substantial nhs_ds detail that the narrative shape has nowhere to put. Both pages already leave most of luscii.json unused, so “migration” is as much about surfacing existing content as adding new content.

2. Scope & method

Both pages were traced from route to component to data field. The matt_demo worktree was read only and not modified. Headings are quoted verbatim from the rendered output. “Used” means the field reaches the live page; many fields exist in JSON but never render.

  • Target: app/products/[slug]/page.tsx → resolveProductNarrative('luscii') → LUSCII_NARRATIVE (lib/content/productNarratives.ts) rendered by components/product/ProductNarrativeView.tsx; types in lib/content/productModel.ts; personalisation via lib/context/*, lib/localData/workspaceData.ts, lib/scenarios/copdRoi.ts.
  • Source: app/apps/[slug]/page.tsx → AppDetailClient + PdpCommissioningSnapshot + PdpTabs → section components in components/AppDetailSections.tsx, app/apps/[slug]/pdpBlocks.tsx, components/DeploymentRegisterTable.tsx, components/DeviceClassDetails.tsx; data from content/apps/luscii.json.

A. Gold-standard content map (matt_demo)

The page is a single scroll: chrome (hero, key-facts KPI strip, “on this page” nav, local context selector) followed by eight numbered narrative sections. Content comes from a two-layer model: the curated LUSCII_NARRATIVE object supplies the story; luscii.json supplies selected facts (logo, conditions, deployments, case studies, NICE refs, demo links). Where both exist, the narrative wins.

Personalisation is the differentiator. Sections 3 and 4 recompute from CommissionerContext (URL params or cookie) + content/local/workspace-deployments.json (e.g. West Yorkshire eligible: 89,000) + the COPD ROI engine. None of this exists on nhs_ds. Note the scenario cohort is currently hard-coded (500 patients) rather than wired to the local funnel.

H. Key decisions & risks

DecisionOptionsRecommendation
Page model (a) Replace the tabbed PDP with the narrative page; (b) Two pages (narrative lead + catalogue detail); (c) Hybrid: one page, narrative spine on top, deep catalogue detail retained below/expandable. (c) Hybrid. Gets the gold-standard story without orphaning the substantial nhs_ds detail (Section E). Avoids a second URL to maintain.
Narrative authoring burden Hand-curate per product vs auto-generate from JSON Curate the high-value sections (problem, how-it-helps, economics, how-to-buy) for flagship products; fall back to a JSON-derived narrative for the long tail (matt_demo already has buildNarrativeFromApp as a model).
Personalisation scope Full geography engine now vs static “national” baseline first Ship Round 1 with a national baseline; add geography in Round 2 so the story lands before the engine is built.
Content accuracy — Resolve price, device-class and proposition conflicts (Section F) before anything is commissioner-facing. These are credibility risks, not cosmetics.
Feature parity — Share/PDF, shared view, and Express interest must survive the restructure. Treat as acceptance criteria, not nice-to-haves.

I. Template for other products

Distilled from Luscii so the next product (myCOPD recommended) can follow the same path:

  1. Map the source. List every content/apps/{slug}.json field and whether it renders today.
  2. Curate the spine. Write the narrative object: problem, how-it-helps bullets, pathway model, how-to-buy framing. Keep pathway moment distinct from sibling products (e.g. Luscii = monitoring hub; myCOPD = discharge bundle).
  3. Reuse facts. Point Assurance, NHS experience, “making it work” and commercial detail at existing JSON; normalise the evidence schema once.
  4. Resolve conflicts. Reconcile price / device class / proposition against a single source of truth.
  5. Layer personalisation. Add geography + effect-size claims; reuse the ROI engine where the condition has one (COPD today).
  6. Protect detail. Run the orphan checklist (Section E) so nothing rich is dropped.
  7. Confirm parity. Share/PDF + EOI still work; a11y + print pass.
