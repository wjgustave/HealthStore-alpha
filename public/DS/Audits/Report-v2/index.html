2.2 #005EB8 → var(--nhs-blue) sweep

--nhs-blue is exactly #005EB8, so each swap is invisible. The sweep covered CSS-context uses only: Tailwind arbitrary values (text-[#005EB8] → text-[var(--nhs-blue)]) and inline DOM style literals (color/background/borderColor/outlineColor, plus the #005EB8 stop inside gradients).

Swept

  • Tailwind arbitrary classes: text-/border-/ring-/from-[#005EB8].
  • Inline style colour literals on DOM elements.
  • Gradient colour stops in inline styles.
  • .app-card:hover border in globals.css.

Deliberately left (tracked, not silent)

  • The --nhs-blue token definition itself.
  • SVG fill in public/**; conditions.json; ADDING_APPS.md.
  • Chart colour map (DashboardCharts.tsx) — CSS vars may not resolve in chart contexts.
  • Multi-colour JS constants (storeAccent.ts, Badges.tsx, ConceptStepsBand.tsx) — folded into the Button / badge rounds.

3. Button decision Done

Shipped: one React <Button> at components/ui/Button.tsx drives every action. The variant set below was approved (3.1), the four style choices applied (3.2–3.5: BTN-3 took Option B, the blue-tinted toggle), and all 12 instances migrated (3.6).

3.2 Choice BTN-1 — primary corner radius

Option A — --radius-md 8px (recommended)

Matches today’s dominant rounded-lg (8px) on login/EOI/PDP CTAs. Lowest-churn.

Option B — --radius-lg 12px

Softer, more contemporary; aligns buttons with card radius. Slightly more visible change.

3.3 Choice BTN-2 — primary hover shade

Option A — #004B8C (recommended)

The shade already hardcoded on login, PDP hero and EOI submit hovers. Zero change.

Option B — --nhs-dark #003087

Uses an existing token (no new hex), but a darker, higher-contrast hover.

3.4 Choice BTN-3 — toggle “on” state (Save / Compare)

Option A — teal (was recommended)

Today’s exact treatment (#E1F4F5/#004B50). Distinct from the blue primary, reads clearly as “active”.

Option B — blue-tinted Chosen

Single-hue system (all blue), fewer colours overall; less differentiation from primary.

3.5 Choice BTN-4 — icon-button radius (AI send)

Option A — --radius-md 8px (recommended)

Consistent with primary buttons and inputs.

Option B — keep rounded-xl 12px

Preserves the current AI send button look exactly.

4.2 Choice MOD-1 — how the drawer relates to Modal

Option A — <Modal variant="drawer"> (recommended)

One component, one trap implementation; variant switches centred dialog vs right slide-over. Fewer moving parts.

Option B — separate <Drawer>

Distinct component that shares the useFocusTrap hook. More files, but keeps drawer-specific animation/markup cleanly apart.

4.3 Choice MOD-2 — AI drawer portal

Option A — move into a portal + trap (recommended)

Consistent stacking/z-index with the modals; gains a real focus trap and focus restore. Behaviour parity across all overlays.

Option B — keep inline, add trap only

Smaller diff (preserves the current mounted-and-translated animation), but keeps the drawer’s separate stacking model.

5.3 Choice RAD-2 — how to wire it

Option A — Tailwind @theme remap (recommended)

Point Tailwind’s radius scale at the tokens, so existing rounded-lg etc. automatically resolve to the scale. Smallest churn in JSX.

@theme {
  --radius-md: 8px;
  --radius-lg: 12px;
  --radius-xl: 16px;
}

Option B — explicit utilities

Rewrite to rounded-[var(--radius-lg)] at each site. Most explicit/greppable, but touches every rounded-* usage by hand.
