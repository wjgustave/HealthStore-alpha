Toasts

Transient feedback for actions — save / remove, copy, comparison changes, and provider load failures — goes through one global service rather than per-feature inline banners. A single ToastProvider is mounted as the outermost provider in AppShell; any client component or provider calls useToast() and gets success, error and info. Toasts render in a top-centre portal, auto-dismiss (errors linger longer), and are manually dismissible.

✓ Saved to your saved apps.
ℹ Added to the comparison tool (2/4).
⚠ Couldn’t save — try again. 
const toast = useToast()
toast.success('Saved to your saved apps.')
toast.info('Removed from the comparison tool.')
toast.error('Couldn’t save — try again.')

// optional inline action (e.g. Undo) for recoverable destructive one-clicks
toast.info('Comparison tool cleared.', {
  action: { label: 'Undo', onClick: () => restore() },
})
Toasts accept an optional action ({ label, onClick }) rendered as an inline button before the dismiss control. This is how a destructive one-click such as Compare “Clear all” stays recoverable (clear immediately, offer Undo) instead of gating it behind a confirm dialog.

Toasts vs alerts

Use a toast when…Use an inline alert / banner when…
Confirming a transient action (save, copy, add to compare).The message is persistent context (e.g. “saving unavailable”, shared read-only view).
Surfacing an action or load failure that has no on-screen home.A form field needs a tied error (FormField error + aria-describedby).

Live-region semantics

  • success + info announce from a polite role="status" region; error from an assertive role="alert" region, so failures interrupt and aren’t missed.
  • The visible toast is the live region — no duplicate hidden announcer.

Accessibility

  • Danger uses role="alert" (assertive); info/warning use role="status" (polite).
  • The icon is decorative (aria-hidden); meaning lives in the text and the leading bold word.
  • Don't rely on the tint alone — keep the "Info/Warning/Danger" label.

Do

  • Reserve danger for genuine errors/blocks.
  • Keep messages short and specific.

Don't

  • Stack many alerts at the top of a page.
  • Use an alert where a badge or inline hint suffices.
